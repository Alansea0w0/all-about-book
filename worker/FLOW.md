# 共读小屋本机回信流程

## 边界

- 网页可在任意设备使用，只负责登录、保存小安的消息和显示回复。
- Supabase 是信箱和共读资料库，不运行 Codex，也不保存 Codex 登录凭据。
- 家中电脑上的取信员负责读取信箱、调用固定的“共读甘棠”任务、写回回复。
- OpenRouter 是网页中的独立备用通道，不冒充固定的 Codex 共读任务。

## 一封信的完整路径

1. 网页先把小安的新内容写入 `discussions`，角色为 `me`。
2. 网页向 `codex_requests` 新增一条 `queued` 请求，并保存书籍、对话、消息和是否附带上下文。
3. 取信员轮询最早的可用请求，用条件更新把它从 `queued` 领取为 `processing`；多个实例同时看到它时也只有一个能领取成功。
4. 取信员按请求中的 `user_id`、`book_id` 和 `conversation_id` 读取书目、摘录、问题、进度和最近讨论。
5. 取信员为这一封信临时启动 Local Codex Bridge 的本机 stdio 会话。Bridge 使用 Codex 桌面版当前随附的原生 `codex.exe`，恢复固定任务并开始一轮只读、无需外部批准的回复。
6. Bridge 等待该轮结束，只返回最终回复正文；需要批准、超时或失败时不擅自放行。
7. 成功时，取信员先向 `discussions` 新增角色为 `syzygy` 的回复，再把原请求标为 `completed` 并记录回复 ID。
8. 失败时，请求被标为 `failed` 或 `needs_attention`，不自动重试。终端只记录脱敏后的短错误，方便定位。
9. 网页轮询请求状态；完成后重新读取讨论，离线或超时则保留信件，等待取信员上线。

## 最小数据库权限

`service_role` 对 `books`、`excerpts`、`book_questions`、`check_ins` 和 `discussions` 只有读取权限，对 `discussions` 另有新增权限。它对这些表没有更新或删除权限，也没有 `conversations` 权限。`codex_requests` 是取信员自己的队列表，需领取和完成请求，因此保留完整权限。

网页用户仍由现有 Supabase 登录和 RLS 限定为自己的数据。本流程不修改既有 RLS、登录设置或认证方式。

## 看似重复但有意保留的部分

- 常驻的外部 Local Codex Bridge 隧道与取信员按信启动的 stdio Bridge 用途不同。取信员走纯本机 stdio，不需要把隧道密钥或网络入口交给网页。
- OpenRouter 通道只作电脑离线时的云端备用，不与固定 Codex 任务共享身份或连续记忆。
- 网页同时保存用户消息和请求记录，是为了让原话即时可见，并让失败请求可审计；请求不会复制成第二条讨论。

## 当前验证状态（2026-09-11）

- 最小权限已经在线验证。
- 取信员启动时会一次性检查队列和五张只读表，检查失败便停止，不再吞掉第一封信。
- 已移除四个临时诊断脚本；运行时只剩网页、Supabase 队列、取信员和 Bridge 四段。
- 已确认取信员曾误用旧全局 Codex `0.147.0`，而固定任务由 `0.153.4` 创建；旧版只读结果缺少新版能正确恢复的模型信息，这是当前最有力的失败根因。启动逻辑现优先选择桌面版当前随附的 `0.153.4`。
- 旧失败请求只按授权重试过一次，仍保持 `failed`，没有回复 ID，也没有在固定任务中创建新一轮。版本修复后尚未再次投递它。

下一次端到端验收应由网页新建一封测试信；不要再次复用旧失败请求。验收条件是：请求只领取一次、固定任务新增一轮、`discussions` 只新增一条甘棠回复、请求最终为 `completed` 且回复 ID 对得上。
